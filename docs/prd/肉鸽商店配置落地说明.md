# 肉鸽商店配置落地说明

> 落地范围：**配置表（Excel + JSON）+ 代码接入**。
> 设计稿来源：`docs/hero-design/`（30 英雄 / 293 道具 / 30 额外技能 / 20 击杀 Buff）。
> 商店规则口径：本文件 §1（来自策划确认，覆盖 `肉鸽塔防_局内成长与经济系统.md` §3 的旧稿）。

## 0. 一句话结构

**商店道具就是遗物**：293 件 dota2 道具在 `relics.json`（id **1001~1293**）。
**效果是原子化的**：一件道具的纯属性加成**不各占一条 Modifier**，而是全项目共用 `modifiers.json` 里**唯一一条**
「属性修改」共享模板（id **1000**），道具自己的属性类型 / 数值 / 叠加方式写在遗物条目的 `kv.attrs` 里 —— 即
**「一条效果模板 + 外部参数」**。商店本身只负责「抽什么 / 花多少 / 谁能选」，**不做任何属性计算**。

```
设计稿 data-items.js ──迁移脚本──▶ relics.json(1001~1293，每条带 kv.attrs 属性表)
                                        │ 引用
                                        ▼
                        modifiers.json id=1000「属性修改」共享模板
                        effects: [{ "type":"modify_attr", "attrs_var":"attrs" }]
                                        │
                     AttributeSystem ◀── ModifierSystem ◀── RelicSystem.AddRelic
```

**引用层级（本项目实际是两层）**：

| 来源 | 引用链 | 表数 / 概念级数 |
|---|---|---|
| **遗物** `relics.modifiers[]` | 遗物 → Modifier（`BattleEquipSystem.Apply` 直接 `AddModifier`） | 2 表 / **2 级**，没有「效果」中间表 |
| **技能** `abilities.effects[]` | 技能 → `effects`（**内联一个字段，不占表**）→ `apply_modifier` → Modifier | 2 表 / 3 级 |
| **单位** `units.abilities[]` | 单位 → 技能 → effects → Modifier | 3 表 / 4 级 |
| **Modifier** `events[].actions[]` | Modifier → actions → `apply_modifier` → 另一个 Modifier（**可套娃**） | 1 表 / 3 级 |
| **肉鸽技能** `abilities.effects[]`（`scope='shop'` 的行，id 101~130） | 技能 → effects → Modifier | 2 表 / 3 级 |
| **击杀 Buff** `kill_buffs` | `attr_id` + `per` **直算属性，不过 Modifier** | 1 表 / 1 级（旁路，待统一） |

「效果」不是一张表，而是**一套词汇**（`game/excel_table/EffectTypes.ts`）：`modify_attr` / `apply_state` /
`tick_damage` / `tick_heal` / `tick_apply_modifier`，被 Modifier 的 `effects`（声明式、轮询）与技能 `effects`
（命令式、执行一次）共用。所以「遗物 → Modifier」保持两层，不需要第三个跳板。

## 1. 抽取规则（口径）

| 项 | 值 | 配置键（`shop_constants`） |
|---|---|---|
| 池子 | **遗物(道具) + 技能 混合池**（种类比例由「技能配额」决定，不再是固定的池权重） | —（见下一行） |
| 技能配额 | 一轮里技能选项 **0~2 个**：先按 **20%** 掷「这轮有没有技能」，再按 **1 个 70% / 2 个 30%** 掷个数；剩下格子全是遗物 | `skillDrawChance` / `skillCountWeight` / `skillMaxPerDraw` |
| 每次抽取展示 | **4 个** | `optionCount` |
| 每次可选择 | **1 个**（选后本次其余置灰） | `pickCount` |
| 抽取费用 | **50 起，每次 +50，200 封顶**（50/100/150/200/200…） | `drawCostBase` / `drawCostStep` / `drawCostCap` |
| 阶段重置 | 不重置（整局累计，封顶后保持） | `drawCostResetEachPhase` |
| 品质概率 | 按**英雄等级段**加权（白/蓝/黄/红）**不变：每个格子仍逐格 roll 品质** | `shop_draw`（4 档） |
| 越阶 | 有概率抽到**下一阶段**的内容 | `shop_draw.upgrade_chance` + `stageMaxByPhase` |
| 广告 | ① 免费抽一次 ② 在已置灰选项里**额外选 1 个** | `adFreeDraw*` / `adExtraPick*` |
| 技能槽 | **4 格**：槽 0 = 英雄专属（永久锁定不可解锁），槽 1~3 可锁定/解锁；重复抽到同名技能 = 升 1 级（`max_level` 封顶，满级后不再进池） | `maxSkillSlots`（可锁定槽数 = 3；**目前是设计常量、无消费方**，4 格写死在 `SkillSlots.SKILL_SLOT_COUNT`）/ `duplicateSkillUpgrade`；规则在 `battle/SkillSlots.ts` |
| 遗物唯一性 | 每局唯一（`RelicSystem` 自带去重）；技能**只在满级后**才移出池（重复抽到 = 升级） | —（已内置） |
| 换英雄 | **等级 / 经验 / 装备 / Buff / 技能槽都不变** | —（见 §3「换英雄不变」） |

抽取流程（`battle/RelicDraw.ts` 出规则、`battle/RelicShop.ts` 走流程）：

```
扣费 → 掷本轮技能配额：20% 有技能（skillDrawChance）→ 再按 70%/30% 掷 1 个还是 2 个（skillCountWeight，上限 skillMaxPerDraw）
     → 循环 4 次：
        品质 = 按 shop_draw 的等级段权重加权 roll
        若 品质.stage > stageMaxByPhase[阶段-1]：
            以 upgrade_chance 概率「越阶」保留，否则降档到当前阶段最高品质
        遗物池 / 技能池各自按 品质 + 阶段 过滤出候选（技能满级的、遗物已有的都不进池）
        配额还没用满 → 先取该品质的技能（按 weight 加权）；技能为空才退回遗物；配额已满 → 取遗物
     → 配额补齐：某品质里没有技能可选时，把遗物候选换成阶段内任意技能（池子空了就放弃）
→ 展示 4 选 1；选择后其余置灰；再来一次需重新付费
→ 选中后按种类分流：遗物 → RelicSystem.AddRelic；技能 → SkillSlots.grant（升级 / 填空槽 / 替换最低索引的未锁定槽）
```

**阶段推导**：遗物不落 stage 列，由 `rarity` 推导（白 1 / 蓝 2 / 黄 3 / 红 4）；技能用 `abilities.json` 里
`scope` 含 `shop` 的行的 `stage`（原 `shop_skills.stage` 列，表已并入 `abilities`）。

## 2. 属性加成：固定值 vs 百分比

两者都写在原子效果 `effects[].attrs` 的条目里，靠 **mode**（叠加方式，条目第三项）区分（`AttributeStackMode`）：

| mode | 含义 | 配置值口径 | 结算 |
|---|---|---|---|
| `add`（属性默认） | **固定值**加成 | 缩放型属性 int = 值×100；其余填原值 | `final = base + Σv` |
| `percent` | **对基础属性的百分比加成** | **百分数**：`14` = +14%（对所有属性一视同仁） | `final = base × (1 + Σv/100)` |

`percent` 的三条关键性质：

1. **只对基础值乘算**，固定值加在百分比之后：`final = base × (1+Σ%) + Σ固定值`。
2. **同类加法叠加、不复利**：两件 +14%/+18% → `×1.32`，不是 `×1.14×1.18 = ×1.3452`。
3. 与 `multiply` 的区别就在这里 —— `multiply` 的配置值是**小数**（`0.14`）且逐条相乘，**百分比加成不要用它**。

实测（`AttributeSystem` 真代码断言，base 攻击力 100）：

| 配置 | 结果 |
|---|---|
| `[[3, 14, 'percent'], [3, 18, 'percent']]` | 132（加法叠加） |
| 再加 `[[3, 20, 'add']]` | 152 |
| 同样两条改用 `multiply`（0.14 / 0.18） | 134.52（复利） |
| 攻速（缩放型，base 1.2）`[4, 14, 'percent']` | 1.368 |
| 攻速 `[4, 50, 'add']` | 1.7 |

### 迁移产出的实际写法

```jsonc
// relics.json —— 一件道具（压制之刃）：属性与数值写在自己条目里
{
  "id": 1001, "name": "压制之刃", "rarity": "common", "icon": "…",
  "description": "攻击力 +14%；砍树；压制",
  "modifiers": [
    { "modifier": 1000, "duration": null, "kv": { "attrs": [[3, 14, "percent"]] } }
  ]
}

// 多属性道具（圆环）：一条 kv.attrs 装完整张属性表
{ "id": 1006, "name": "圆环",
  "modifiers": [{ "modifier": 1000, "duration": null,
    "kv": { "attrs": [[1, 40, "add"], [4, 2, "add"], [7, 0.8, "add"], [6, 0.28, "add"]] } }] }

// modifiers.json —— 全项目唯一一条「属性修改」共享模板（id = MODIFY_ATTR_TEMPLATE_ID）
{ "id": 1000, "name": "属性修改", "is_debuff": false, "is_hidden": true, "dispel_level": 0,
  "duration": -1, "stack_mode": "none",
  "effects": [{ "type": "modify_attr", "attrs_var": "attrs" }] }
```

`effects` 是**原子效果列表**（一条效果一件事），共 5 种：`modify_attr`（属性条目，支持 `attrs_var` 外置整表与
条目级 `var` 单值覆盖）/ `apply_state`（状态）/ `tick_damage` · `tick_heal` · `tick_apply_modifier`（周期，**每条自带计时器**）。
旧的 `properties` / `states` / `tick` 三列已废弃（迁移脚本 `tools/excel_export/scripts/migrate-modifier-effects.ts`，幂等）。

**属性修改的四条通道都收敛到同一条效果**：

| 场景 | 写法 |
|---|---|
| 遗物/道具（常驻） | `relics.modifiers[{ modifier:1000, kv:{attrs} }]` → `BattleEquipSystem.Apply` |
| 技能临时改属性 | `abilities.effects[{ type:'modify_attr', attrs, duration }]` → `EffectExecutor` 转成同一个模板 |
| Buff/DoT 自带属性 | `modifiers.effects[{ type:'modify_attr', attrs }]` |
| 模板 + 幅度参数 | 条目写 `{ "attr":5, "value":-90, "var":"slow" }`，施加时用 `kv.slow` 覆盖数值 |

**多个被动各算各的 cd**：每条被动是一条独立 Modifier（自带 `cd`），`Modifier.cdRemaining` 各持一个计时器，
由 `ModifierSystem.Tick(dt)` 随 `ctx.Tick` 一起推进；`IsReady()` / `Trigger()` 按实例粒度判定与重置。
**每条周期效果也各算各的间隔**（`Modifier.advanceTicks` 按效果粒度计时）。

## 5. 修改流程

```bash
# 常规改数值：改 Excel → 导表
cd tools/excel_export
npm run export          # excel/*.xlsx → assets/resources/tb/*.json
npm run verify          # 往返自检（JSON → Excel → JSON 必须无损）
npm run check:shop      # 抽取体检：空池 / 重复 / 费用曲线 / 品质与池比例分布

# 设计稿更新后重新迁移（幂等：只替换 id ≥ 1000 的段，手工的 id<1000 条目保留）
node tools/excel_export/scripts/gen-shop-from-hero-design.ts
node tools/excel_export/scripts/migrate-modifier-effects.ts   # 一次性：旧三列 → effects（幂等）
node tools/excel_export/scripts/merge-shop-skills-into-abilities.mjs   # 一次性（已执行）：shop_skills 30 条换 id 段并入 abilities（幂等）
npm run import -- --force --table relics,modifiers,abilities,kill_buffs,shop_draw
npm run export
```

**id 约定**：遗物 `1000+道具id`（1001~1293）；**属性修改共享模板固定 id = 1000**（`MODIFY_ATTR_TEMPLATE_ID`，
`1000+it.id` 与它不冲突，因为道具 id 从 1 起）。手工 Modifier 占 1~26，**2000 段预留给未来的道具被动**。
`shop_constants.json` 是**手写源**（脚本不读也不写）。

导表时会自动做**原子化校验**（`tools/excel_export/src/core/crossCheck.ts`）：`effects` 的类型 / 状态名 / 周期间隔、
`attrs` 的属性编号与叠加方式，以及**遗物条目是否给齐模板要求的 `kv` 参数**（缺了就报错，避免"挂上去没效果"）。
