- **打击反馈体检（2026-10 落地）= `tools/hit-feel-audit/audit.mjs`（`npm run audit:hitfeel`，178 条）**: 陪打击反馈 B0+B1（决策层）+ B2（印痕层）+ B3（屏幕层/血条）+ B4（音效账本）一起落地 —— 把真 `HitFeelConfig` / `HitFeelDirector` / `HitVfxLayer` / `HitScreenLayer` / `HpBar` 用 `transpileModule` 编成 CJS，桩掉 `battle/index`（转发到真 `types.js`，事件名不手抄）与 **`cc`（换成"记账画布 + 一棵极简假节点树"：不渲染，只记画了几个圆、几段折线、几个矩形、线宽与坐标；节点支持 `addChild/getChildByName/getSiblingIndex/setSiblingIndex/getComponent/addComponent`，所以"残影条插在血条之前"这种**结构**也能断言）**，再用**假总线 + 假时钟**真跑。**它验的是"肉眼验不了"的硬口径**：① **时间税 ≤3%**（典型 60s 节奏实测 0.97%；最坏"每帧一发暴击"顶在 3.00%）② **1s 滑动窗口内顿帧 ≤30ms**（逐帧采样滑窗**独立复算**，不信导演自己那本账）③ **位移 ≤6px 且同帧 20 连击只产生 1 次** ④ **每档画出的图元数 = 档位表**（环层数 / 刻度段数 + 对位十字两臂 / 碎片块数，八档逐个对）⑤ 环最终扩散到 `ringRadius`（误差 ≤3%）、只描边不填充、刻度垂直于伤害方向、密度 k 真的乘到尺寸上 ⑥ **三级上限**（每秒新建 ≤60 丢弃并计数 / 并发 ≤24 且**淘汰最弱档**——用"暴击印痕活下来、环半径压过 T0"验 / 碎片 ≤48）⑦ 起手虚线的段数·段长·方向、换局无残留、空场不重绘 ⑧ **墨闪只在 T5/T6/T7、峰值 α = 档位表、50ms 归零、1.5s 冷却期内丢弃计数** ⑨ 四角角标 8 段贴边且用 `c-danger`、连击 2.5s 断连后淡出清零、墨闪整屏矩形 ⑩ 落款 1.2s、奖励**飞到 HUD 锚点**（误差 <8px）、无锚点退化成右上、并发 ≤12 ⑪ 残影条**插在血条之前**、借 SpriteFrame、单调收敛、0.3s 收掉大半、回血直接跟到位。另有：档位判定 12 例（含「DoT 与普攻同档」）、密度 k∈[0.55,1]、**注入 200ms 卡顿连跑 600 帧**无 NaN/无越界、换局 `reset/unbind` 无残留订阅、档位表自洽、**音效账本（B4：50ms 内 ≤2 声 / 同帧只出最强档那一声 / 超限丢弃计数 / 英雄出手 + 同帧命中正好用满 2 声 / 怪出手不响 / 音量不吃密度 k / 未接播放器也照记账 / 换局清窗口；用**假播放器记账**，所以完全不依赖任何音频文件）**。
  · **为什么要给 `cc` 打桩而不是静态扫代码**：印痕/屏幕层值得验的东西全在"算了什么、画了几笔、坐标是多少、节点挂在哪"这一层，这些不需要 GPU；真正需要眼睛的部分留给设计文档 §8.2 的主观验收。⚠ 桩必须放在 `<tmp>/node_modules/cc/`，不能放 `<tmp>/assets/scripts/` —— 真源码的 `import ... from 'cc'` 是**从它自己所在目录逐级往上找** `node_modules` 的，放对位置才能让任意深度的模块解析到**同一个实例**（`getComponent(Graphics)` 靠类同一性判断）。
  · **桩要"像真的"，但不能替真源码兜底**：假 `Component` 必须带 `isValid`（真引擎有，`HpBar` 借 SpriteFrame 时会判 `src.isValid`），但**不该**模拟 `@requireComponent(UITransform)`——正是这条"不兜底"逼出了 `HpBar` 里"显式取或补 UITransform"的写法（不依赖引擎的隐式组件依赖，更稳）。
  · **它当场抓出的三处"表与实现不一致"**（教训：**只有真跑才看得出来**）：① 档位表写"暴击顿帧 45ms"，而账本上限是 30ms/秒 → **45ms 永远拿不到**，于是把常规档位统一改成 30ms（峰值档位 T5/T7 才是 60/90ms）；② 断言"印痕元素数随档位单调"失败 —— 复查后判定**是断言错了不是表错了**：`ringRadius` 是**按体型**定的（Boss 体型 ×1.5~2，26px 环在它身上看不见），力度由刻度条数/环层数/十字承载 → 改成"命中链单调 + Boss 环半径严格大于暴击"；③ B2 自己写的"相距 > 合并半径不合并"用例**第一次也写错了**（`far` 的坐标写成 `mergeRadius*2`=160，而目标在 x=100 → 实际只隔 60px，正落在合并半径内）。
  · **B3 新写的用例里又踩了三个同类坑**（都记在这里，下次写体检脚本直接避开）：① 屏幕层的墨闪读的是 `HitFeelDirector.active`，而**上一组留下的导演**会让"精确数笔画"的断言多出一个整屏矩形 → 需要精确计数的组开头先 `HitFeelDirector.active = null`；② 一个事件要同时喂给导演和屏幕层时，**让它们共用同一条假总线**（各用各的 bus → 只画出一半，第一次就是这么写错的）；③ 想"一次推 400ms"来跳过角标寿命，`update` 内部会把 dt **钳到 50ms**（掉帧守卫）→ 只能老老实实推小帧。
  · **同族的教训**：`EntityView` 的位置脏检查原来比对 `entity.position`，加了表现层抖动后**怪静止时永远看不到抖动**（位置没变就 return）→ 必须改成比对**最终写入值**；`HpBar` 的高度补偿原本现读 `parent.worldScale`，加了受击膨胀后**受击那一帧血条会跳高** → 改成用 `attach` 传入的**基准 scale**。

- **打击反馈音效（B4，2026-10 落地）= `tools/hit-feel-sfx/`（配方 + 离线渲染 + 试听 + 对账）**: 「**素材不是找来的，是渲出来的**」—— 工程原本 `assets` 下 **0 个音频文件**，与其去挑一堆与浅底图纸风不搭的第三方音效，不如把**演示台 §3 那份为本作调过的 Web Audio 合成参数**搬进一个离线渲染器批量出文件。产物 = `assets/resources/sfx/` 的 **16 个 wav**（11 个音 + 5 个音高变体，139KB，16bit WAV / 22050 单声道 / 逐条峰值 0.80），**零第三方素材 → 零授权义务**。
  · **四个文件各自只干一件事**：`design.mjs` = 「要什么声音」（11 条配方 + 5 条变体 + 渲染全局设置，**唯一真源，不做 DSP**）；`render.mjs` = 「怎么算」（零依赖 DSP：白噪声→二阶带通、指数扫频、4ms 起振 + 指数衰减 + 1.5ms 收尾；`--check` 全内存重渲逐字节比对且**绝不写盘**）；`audition.html` = 试听（按档听 / 变体单听 / 两个节奏场景听"合并与节流"）；`check-drift.mjs` = 对账。
  · **三道门禁各管一段**（别互相替代）：`render.mjs --check` = **字节层**（盘上 wav ↔ 配方、快照是否新鲜、配置引用的键是否都在盘上）；`check-drift.mjs` = **口径层**（`HitFeelConfig.ts` ↔ 试听页内嵌快照 ↔ 素材文件集合，**这是素材门禁**，缺文件即失败）；`npm run audit:hitfeel` ⑰ = **代码层**（节流账本真的成立吗，**缺素材只警告不判失败**）。
  · **确定性是对二进制产物的硬要求**：噪声种子按键名派生（`mulberry32`），所以同配方永远出**逐字节相同**的文件 —— 否则每次重跑，git 里都会多出 16 个"改了但其实没改"的二进制 diff。（落地时连跑两次验证哈希一致。）
  · **试听页不能自己维护数字**：它是静态 HTML，没法在 `file://` 下 import TS，所以音量/键名很容易与 `HitFeelConfig.ts` 悄悄分叉（**改音量的人不会想到要翻一个 html**）→ 页面里那段 JSON 由 `check-drift.mjs --write` 从真源生成，`check-drift.mjs` 不带 `--write` 时只对账，不一致就红。**同类先例**就是演示台的 `check-drift.mjs`。
  · **两个独立解析器互相对账是有价值的，不是重复劳动**：`check-drift.mjs` 与 `render.mjs` 各自文本解析了一遍 `HitFeelConfig.ts`（都不编译、不 import TS），`check-drift.mjs` 的第 ④ 节专门比对两者结论。落地时真抓到一次**只有交叉才能发现**的错：`render.mjs` 第一版把**数组字面量**当对象做括号配对 → 变体后缀表静默解析成 `['']` → 5 个 `_v2/_v3` 被误判成"没人引用"。
  · **试听页本身也被真跑验过**：用临时静态服务在真实浏览器里打开，点「过载」场景确认计数器按"50ms 内 ≤2 声"走（实测 ~1s 内 响 18 / 丢 15 / 窗口内 2），并且页面里挂了一条 `window.onerror` 横幅 —— 工具页出错如果只烂在 console 里，使用者只会以为"没声音"然后把问题报到别处。
  · **踩过/查清的引擎口径**：`AudioSource.playOneShot(clip, volumeScale)` **没有音高参数**、`AudioSource` 也没有 `playbackRate` → E3 音高随机只能**预渲染变体**；`AudioMgr.playSFX` 强制补 `sfx/` 前缀，而 `ResManager.loadBundleRes` 会**把首段当分包名** → 原来的顺序（先 bundle）会让每次首次加载都白打一条 `分包:sfx加载失败`，已改成**先 `resources.load` 再退回 bundle**；`.meta` 要等编辑器首次导入才生成，**必须随提交入库**。

- **⚠⚠ 改这些工具文件时别用 `Get-Content | Set-Content`（2026-10 真踩过，代价是重建整个生成器）**：PowerShell 5.1 的 `Set-Content` **默认按 ANSI(GBK) 写盘**，把 UTF-8 的 `gen-prompts.mjs` 写成了 GBK —— 中文注释与若干中文字符串被破坏（294 处无效 UTF-8），`node` 直接 `SyntaxError`，而且**文件没被 git 跟踪、无法回滚**。当时的救法（值得复用）：**英文常量与代码是 ASCII，全部完好**，而**全部中文字符串都留在了生成产物里**（`prompts.json` 的 `model`/`note`/`deliver_size`、`prompts.csv` 的 `prompt_edit_zh`、`prompts.md` 的标题与说明），于是按"英文逐字保留 + 中文从产物反推"重建，再用**三条独立验证**确认忠实：① 风格段 8 句与事故前读到的原文逐字一致；② 损坏文件里 139 条 ASCII 字面量**全部**出现在重建文件里；③ 从损坏文件的素材独立拼一条提示词，与产物**逐字相同**。**结论：这类"生成器 + 产物"的搭配天生有备份价值 —— 产物就是生成器的可验证快照；改文件一律用编辑器/`[System.IO.File]::WriteAllText` 这类显式 UTF-8 的工具。**
  · **2026-10 第二次翻车（同类事故，但这次有个"万能兜底"）**：这次是用 `Get-Content -Raw | Set-Content -Encoding utf8` 去批量替换一个词的调用点 —— 结果同一条链路把 UTF-8 读成 GBK 再按 UTF-8 写回，**中文与注释全变乱码**（还多了个 BOM）。踩点在于：① PowerShell 5.1 的 `-Encoding utf8` **会写 BOM**，而 `Get-Content` 不带 `-Encoding` 时按**系统 ANSI（中文机 = CP936）**读；② 受害文件是**未被 git 跟踪的新工具**（`tools/hit-feel-audit/audit.mjs`），没有历史可回滚；③ 反向变换（把乱码按 CP936 编回去）**不能完全还原** —— 中文后面紧跟 ASCII 时那个字节已被解码器吞成 `?`，`IndexOf('⑫')` 直接找不到。
  · **兜底方案（值得记牢）：DSH 的会话记录就是每一次写盘的逐字日志。** `$env:DSH_SESSION_JSONL` 指向本次会话的 `session.jsonl.zstd`，里面有**每一次 `write` / `edit` 工具调用的完整参数**。恢复步骤（当时实测可行，27 次操作 0 冲突）：
    1. **解压**：这个 `.zstd` 是**多帧拼接**的（会话边写边追加），`zstdDecompressSync(整个文件)` 只出第一帧（195 字符）、流式 `createZstdDecompress` 会报 `Unknown frame descriptor` → 正确做法是**按 zstd magic `28 B5 2F FD` 切开**，对每个偏移 `zstdDecompressSync(buf.subarray(off))`，成功的拼起来（10 MB 文本、9707 条记录一次成功）。
    2. **筛操作**：遍历 `type === 'tool/call'` 且 `name` 是 `write`/`edit`、`JSON.parse(data.arguments).file_path` 命中目标文件的记录，**按出现顺序**排列。
    3. **重放**：从最后一个 `write` 的 `content` 起，依次做 `old_string → new_string`（`replace_all` 为真就全替换）。**判据：每一次 old_string 都必须命中** —— 只要全部命中（哪怕一次）就证明重放文本与损坏前的文件**逐字节一致**（因为每个 old_string 都是当时照着那份文本写出来的）。
  · **两条可迁移的结论**：① 这套"从会话记录重放 write/edit"对**任何本会话改过的文件**都成立，是比 git 更细的兜底（未跟踪文件也在内）；② 但它只在**同一个会话**里有效 —— 跨会话的新窗口里就没有这条日志了，所以"改文本文件一律用显式 UTF-8 的工具"这条纪律不能因为有了兜底就放松。
