- **遗物 / Modifier 的时长口径（踩过：遗物加的属性"过一帧就没了"，表现为 UI 刷新时又变回去）**: **只有 `-1` 表示永久**（`modifiers.json.duration` 必填，`-1` = 不衰减、正数 = 秒）。引用方的 `duration` **留空就是 `null`**（Excel 空单元格导出成 null）= **「没写」，绝不是 0 秒** —— 统一由 `Modifier.normalizeDuration` 归一化：`null` / `undefined` → 回落 `ModifierCfg.duration`，两者都缺省 → 永久 `-1`（`ModifierSystem` 的 refresh/stack/strongest_only 三条刷新时长路径也走它）。旧实现 `duration !== undefined ? duration : def.duration` 把 `null` 当成了显式时长 → `remainingTime = null` → `isPermanent()` 为 false（`null < 0` 不成立）→ 首次 `Tick` 里 `null - dt` 是负数 → 当场判定"已过期"并移除。**遗物效果默认永久**：`BattleEquip.Apply` 传 `entry.duration ?? -1`，**不回落效果模板自带时长**（模板是给技能/临时 Buff 的，如 mod 11「吸血」= 5 秒；借用它会让遗物被动 5 秒后失效）。`relics.json` 的 259 条局内版条目**全是 `duration: null`** → 修之前**每一件有局内版的遗物都是无效的**（属性与被动都只活一帧，靠 `OnRelicAdded` → `syncHeroToStore` 先写好 `battleStore.maxHp` 才"看起来加上了"，下一次受伤/回血/升级同步时又"变回去"）。口径同步在 `docs/数值配置参考手册.md` §8.2。

- **「加最大生命」的满血口径 = `Entity.ApplyWithMaxHpCarry(fn)`（遗物 / 击杀商店 Buff 的唯一入口）**: `hp` 是独立字段、**不会**跟着属性贡献涨（属性是"贡献 → 下次读取时重算"，`hp` 要显式写），所以"满血买 +生命遗物"会凭空出现一道缺口（1000/1000 → 1000/1140），看起来像没加上。口径：**施放前满血 → 当前生命同步 +ΔmaxHp（加完仍满血）；施放前不是满血 → 只抬上限、当前生命不动**（否则"残血买血"等于白送一次治疗）。实现是一层包裹器（取施放前的上限与"是否满血"快照 → 跑 `fn`（内部写 Modifier/`addBase`）→ 按新增的 `ΔmaxHp` 补 `hp`），调用点：`BattleEquip.Apply`（整组遗物 Modifier 包在里面）、`BuffShop.applyStack`（每层一条 Modifier）。**升级不再补满**（2026-11 用户口径）：`Scene_Game_Stage.addBattleExp` 升级时**只按 `growthValues` 抬上限**，当前生命/魔法保持原值（原先的 `hp = getMaxHp()` + `mana = getMaxMana()` 已删 —— 那等于"残血升级白送一次治疗"，把续航压力抹平）。⚠ 只给**永久**上限变化用：临时上限（技能 buff 到期会掉回来）**不要**走这个口 —— 上限回落而当前生命不回落会出现 `hp > maxHp` 的脏数据（HUD 显示 1200/1000），要等下次 `ChangeHp` 才钳回。

- **两处「配了也不生效」的静默陷阱（2026-09，门禁已拦）**: ① **`percent` × base=0 = 0** —— 护甲(6)/生命恢复(9)/魔法恢复(10) 的 `attributes.json.base` 都是 0（英雄收口后不再配这三项），用 percent 恒不生效（36 条词条：护甲 13 + 回血 23，如「统御头盔」护甲 +22% → 0）；规则真源 = `affix-rules.mjs` 的 **`ZERO_BASE_ATTRS`**，`check:affix` 报错（`numeric_percent_zero_base`）、`migrate:affix` 按 `FLAT_CONVERT_BASELINE` 自动折成 `add`（护甲 15% → +1.5、回血 14% → +0.28，描述同步重写）。② **暴击是半套系统** —— `DamagePipeline.rollCrit` 要求 `chance > 0 && mult > 1`，而属性 15 暴击倍率 base 曾是 100（1.0）→ 暴击永远不发生；现定案：**base = 150**、词条值 int = 倍率×100、**词条叠加方式必须显式写 `best`**（**条目 mode 覆盖属性默认 mode**，写 `add` 会变成 `base + Σv` 累加：`+225%` 会算成 375%，实测踩过）；合同真源 = `CRIT_MULT_BASE` / `CRIT_MULT_MODE` / `critTextToMultiplier`，数据修复 = `npm run fix:crit`（幂等：attributes base + 文案承诺的暴击词条回填 + 叠加方式归一，报告 `tools/excel_export/reports/crit-baseline-fix.md`）。**未定案**：1126 水晶剑（蓝档）/ 1242 巨人重锤（白档）文案写了暴击但没有对应词条 —— 百分比型属性黄档起，回填会把门禁打红，`fix:crit` 只报不改（二选一：升档补词条 / 删越档文案）。
- **遗物流派标签（2026-11 落地）= 三张表共用一套 8 个词，且由机制推出来、不手写**: `relics.json` 的 `tags`（1~3 个，**第 1 个是主标签**）与 `abilities.json` / `kill_buffs.json` 的 `tags` **是同一套词表** —— `远程点杀 / 坦克反伤 / 物理暴击 / 法术爆发 / 召唤增殖 / 元素持续 / 经济成长 / 控制减速`（词表真源 = `relic-inner-design.mjs` 的 `RELIC_ARCHETYPES`，落表脚本对未知标签**直接抛错**）。**为什么不手写**：`tagsOf(item)` 从两张规则表推导 —— `HOOK_TAGS`（**43** 条钩子 → 标签，判据是**代码里的真实伤害类型**：`RelicHook_HitPct` / `RelicHook_Chain` 打的是 `DamageType.Magical` ⇒ 归「法术爆发」，`RelicHook_Splash` 打攻击力百分比 ⇒ 归「远程点杀」）+ `ATTR_TAGS`（属性 → 标签）；想显式指定就在 `ITEMS` 里写 `t: [...]` 覆盖。**一条实测口径**：属性只在**这件没有钩子**时才定性 —— 一开始让属性与钩子并列，「坦克反伤」占到 166/268（62%，因为 `护甲/魔抗/闪避/受伤减免/吸血` 大面积作**次要词条**出现在输出件上），收紧后 131 件（49%）；再高就是**白档池子本身以防守件为主**的形状问题，属 B 批补进攻白件的事。⚠ **`召唤增殖` 原先遗物侧 0 件**（40 条钩子无召唤类、本工程无召唤物基建）—— **2026-11 已补齐**：新增 `turret` / `mirror` / `clones` 三条**零基建等价机制**钩子（周期自动开火 / 概率再打一发 / 击杀累积分身 —— **不造实体**，理由见下一条），并挂到 6 件**名字本来就指着一个"多出来的自己"**的遗物上（幻影斧 / 支配头盔 / 三叉戟 / 影刃 / 回响之笼 / 怨灵系带）⇒ **蓝 2 / 黄 2 / 红 2**。⚠ **白档仍然是 0 件、而且应该保持 0**：白档只有属性、推不出「召唤增殖」（物理暴击 / 元素持续 / 经济成长 / 控制减速的白档也都是 0），硬贴标签就是"标签失去区分度"。**消费侧**：`RelicCfg` 已加 `tags?: string[]`（与 `Tb_AbilityConfig` / `Tb_KillBuffConfig` 同形），但**目前没有任何 UI 读它**（商店 4 格仍不显示流派）。

- **遗物属性值的唯一出处：`ATTR_VALUE[品质][属性] × SHARE[属性条数]`（2026-11 改，取代"手写值 + SUPPLY_TOPUP 覆盖"）**: 用户口径是"右边 3 件都是攻击 +8，中间那件还多一条加成，那肯定选中间那件"。根因有两条，**都在池子结构里**：① 白档 107 件只有 **32 种效果**（「攻击力 +8」那一组有 **20 件**完全相同）；② 多属性件**每条都拿满额** ⇒ 属性集合是超集的那件**逐属性全面压过**小的那件（旧池子 `1470 组支配对`，白档 397 / 蓝档 363）。
  · **新机制**：`ITEMS` 里一行只写"这件有哪几条属性"（`a: [3, 16]`，**不写字面值**），`applyBudget()` 按 `ATTR_VALUE`（每档每属性的**单属性满额值** + 叠加方式）+ `SHARE`（单 1.0 / 双 0.75 / 三 0.6）+（代价件再 ×`COST_BOOST`）现算；`MAX_ATTRS_PER_RELIC = 3` 封顶。
  · **为什么这样就没有支配关系**（可证明，`check:pool` 的 B1 是它的回归网）：若 A 的属性集合 ⊇ B 的，则 A 的**条数 ≥** B 的 ⇒ A 在共享属性上的值**≤** B 的（share 单调不增）⇒ 不可能"每条都 ≥ B 且至少一条 >"；集合相同 ⇒ 值完全相同 ⇒ 是**重复件**而不是支配件（重复密度由门禁单独卡：白/蓝 ≤2 件/种、黄/红 ≤4）。
  · **池子形状**（重排后）：白 107 件 / **84 种效果**（改前 32 种）、蓝 80/68、黄 54/43、红 27/23；条数分布 白 14 单 + 40 双 + 53 三。**"每件效果都不一样"是硬需求**：9 条可用固定值属性最多拼出 45 种 ≤2 条的组合，装不下 107 件白档 —— 所以白档允许 3 条属性（`SHARE` 的注释里有这条推导），且**每种组合最多 2 件**。
  · **白/蓝的基准值是校准过的**（不是拍脑袋）：目标是"每局抽到的**期望收益**与现网持平"（`Σ(属性)/件数`），现网白档 攻击 13 / 生命 140 附近、蓝档 20 / 200（改前是 8 / 90 与 10~18 / 90~145，但那时 45 件是"两条都满额"）。
  · **`SUPPLY_TOPUP` 的语义变了**：它现在只做"**把这条属性配给名单里的件**"（`add` = 追加成设计属性，`except` = 这件不加），**不再覆盖任何值**；有上限属性的供给靠"哪些件带它"配平，`gen:relic-design` 会重算表并卡红线（毛供给 ≥ 上限 × min；净额只打印）。
  · **改动的影响面要一起跑**：`npm run gen:relics-inner` → `json2excel --force --table relics` → `npm run export` → `check:pool` / `check:affix` / `audit:attr` / `audit:archetype` / `node tools/boss-balance/sim.mjs`。
  · **数值影响（2026-11 实测，`boss-balance` 40 局）**：中位英雄的最终 Boss TTK **16.9s → 22.5s**（中位 DPS 304 → 230），最慢英雄 26.0s → 32.9s —— **硬判据（最慢 ≤150s）仍绿**；方向与"局内前面太容易"这条既有口径一致（瘦下来的正是旧池子里那些"6 条属性全满额"的怪物件）。
  · ⚠ **`ITEMS` 的 `a` 是 id 数组**（不是 `[[id, value, mode]]`）：任何按 `entry[0]` 读属性的地方都要走 `attrIdOf()`（`tagsOf` 已改；`descriptionOf` / 落表脚本读的是 `resolveFinalItems()` 之后的结果，不受影响）。

- **代价件 / 「有增有减」的词条（2026-11 落地，Brotato 式）**: 口径 = **符号本身就是声明**（普通轴 `value < 0` 即代价；`12 受伤减免` 是**倒置轴**，`value > 0` 才是代价）。判据真源 = `affix-rules.mjs` 的 `looksLikeCost()` / `isCostEntry()` / `classifyCostAffix()` + **`COST_RULES` 白名单**。三条硬口径：① 代价**不受档位门禁约束**（门禁管"低档不许承诺高档**收益**"，代价方向相反）—— `check:affix` 的 `kv.attrs` 与描述解析（`illegalDescriptionClauses`）都已放行；② 代价必须落在**能真减**的属性上：`1/2/3/4/6/7/11/12/16/21/22`（`6 护甲` 是唯一能进负值的轴，min −20，负护甲按 Dota 双曲公式 = 受更多物理伤害）；**不能当代价的**：`闪避(8)/生命恢复(9)/魔法恢复(10)/暴击率(14)/冷却缩减(23)/抽卡折扣(24)/吸血(25)/攻击回复(26)/攻击回蓝(27)`（base 与 min 都是 0，减过去被钳成 0 = "配了却没变"）、`暴击倍率(15)`（`best` 模式）；③ 必须写对该轴的叠加方式 —— **`4/11/12` 的默认模式是 `multiply`**，不显式写 `add` 会走进复利分支（全项目禁用），`7` 默认是 `complement`。**落表必须注意**：代价在 `ITEMS` 里是**独立一列 `cost`**，`resolveFinalItems()` **最后才并进 `a`**（`cost` 字段原样保留）—— 先并进去的话：① 供给配平/预算表会把它当收益（`SUPPLY_TOPUP` 的 `except` 就是为它留的）、② 评审稿与体检分不清"收益"与"代价"（**不能靠符号认**：`12 受伤减免` 是正号代价）。⚠ **只在局内版加代价**（`modifiers_inner`）—— `modifiers_outer` 是永久且不可逆的，减生命会变成不可撤销的惩罚。**验证**：`npm run check:affix` 会打印代价件清单；`npm run audit:attr` 的**「代价专项」**真跑属性链路验 `moved`（真的变了）+ `worse`（方向朝更差，含倒置轴 12），失败即退出码 1 —— 这是必须的，因为逐属性表只挑**绝对值最大**的词条，**代价永远不在它的射程里**。

- **代价件 B 批（2026-11 铺开到 65 件）—— 四条踩出来的口径**（每条都有回归网）：
  ① **价钱必须随档位缩放**：收益按 `COST_BOOST`（白 1.5× / 蓝 1.4× / 黄 1.3× / 红 1.25×）放大，若价钱对所有档都写 −12%，白档就变成"用 12% 攻速换 1.5 份薄收益"的**陷阱件**（玩家全避开 = 这批件不存在）。现价钱 = 白 −6% / 蓝 −9% / 黄 −12% / 红 −15%。
  ② **代价不许落在自己的收益轴上**："最大生命 +168 代价 最大生命 −12%"等于自己抵消自己。选轴时要跳过该件已有的属性。
  ③ **供给配平也不许把代价轴补给这件遗物**（`applySupplyFill` 里那条 `it.cost.some(...)`）：漏了它会出「收益 攻击速度 +31 / 代价 攻击速度 −12%」这种**净额为正的假代价** —— `audit:attr` 的代价专项报的是"方向反了"，而**表里每一条都合法**，只有净额是错的。
  ④ **上限可达性判据用毛供给，不用净额**：净额口径是 5 件代价件时代定的（那时净额≈毛额），铺到 65 件之后光"攻击速度 −12%"这一条就有 −490，于是「攻速净额 284 < 上限 500」被判成"堆不到上限"——**那不是事实**：玩家堆攻速时会**避开**那些把攻速当价钱的件。净额现在只作为"取舍压力"的参考读数打印（`gen:relic-design`）。
  · **标签**：代价条目不产生流派标签，判据按**整条条目**（`[属性,值,模式]`）过滤而**不是按属性 id**（同一条轴可以同时是收益与代价，按 id 过滤会把收益也丢掉）。2026-11 之前这条只写在 `tagsOf()` 的文档里、实现漏了 —— 5 件代价件时看不出来，61 件时有 30+ 件的标签是**代价**给的（「笨重」的攻速 −12% 按 `ATTR_TAGS[4]` 给纯防御件贴上「远程点杀」）。
  · **回归网**：`npm run check:pool`（密度区间 + 支配对）+ `npm run audit:attr`（代价真的生效且方向正确）+ `npm run check:affix`（代价轴白名单）。

- **配表源漂移（2026-09 实测，已按 JSON 方向回灌收敛）**: `npm run check`（xlsx→JSON 只比对不写盘）曾报三张表与 JSON 不一致：① **`relics` id 1~5（手工 demo 遗物）只存在于 JSON，xlsx 里根本没有** —— 这时直接跑 `npm run export`（xlsx→JSON）会**把它们删掉**；② **`units` 2001 哥布林**：JSON 生命 40 / xlsx 生命 100（未定哪个才是策划要的，当前以 JSON 的 40 为准）。处理方向：**以 JSON（线上口径）为准** `npm run import -- --force --table attributes,relics,units` 回灌 xlsx → `npm run verify` 确认往返无损。**两条教训**：脚本改完 JSON **必须**回灌 xlsx；反过来怀疑 JSON 落后于 xlsx 时，先跑 `npm run check` 看清两边差异再决定方向，**别盲目 `--force`**。

- **局内双货币（2026-11 落地）= 金币只给抽卡、击杀数只给 Buff**: **金币**（`hero.gold` → `battleStore.gold`）用于**选英雄刷新 + 遗物抽取**，唯一扣费口 `Scene_Game_Stage.spendGold()`（顺带上报 `spend_gold` 任务/成就）；**击杀数**（`battleStore.killPoints`，只算英雄击杀）用于**击杀商店（Buff/神器）的刷新 + 购买**，唯一扣费口 `battleStore.spendKillPoints()`。两条线互不抢资源（设计稿 `docs/局内刷怪节奏设计.md` §7.1 / §12.6）。落地细节：`killPoints` 与「累计击杀数」是**两个数** —— `killPoints` 是**余额**（花掉会减，HUD 的 `money/kill/value` 显示它），`kills`/`Scene_Game_Stage.killCount` 是**累计统计**（结算与成就 `kill_in_run` 用，只增不减）。价格口径：`kill_buffs.json.price`（12~45，`× price_growth^(层-1)`）与 `shop_constants.killBuffRefreshCost`（**50**）**都是击杀数**，不上浮也不除以 3（÷3 是 60s 短局的老配方，当前长局一局约 1200~1500 只）。

- **`shop_constants.drawCostCap`：`200`（2026-11 上半）→ `0` = 不封顶（2026-11 下半，用户口径「局内遗物的加个会一直涨，之前是 200 就不动了」）**: 遗物刷新费用 = `50 + 25×已付费刷新次数`，**一路涨**。注意 `ShopConfig.getDrawCost` 的写法是 `cap > 0 ? min(raw,cap) : raw` —— **`cap = 0` 表示不封顶，别把它当"免费"**（2026-11 就因为漏了这一条，`tools/boss-balance/sim.mjs` 里一处 `Math.min(raw, cap)` 让抽卡当场变成 0 金币，整套"局内成长"模拟失真）。**这条是螺旋了一轮又回到设计稿**：`docs/局内刷怪节奏设计.md` §12.6 原本就建议"去掉（或 600）"，理由是长局必然撞顶、撞顶后边际成本变常数、商店失效；2026-11 上半被用户口径"最高 200"覆盖过一次，下半又按"会一直涨"改回来。**数值后果**：单局收入 ≈9,120 金时，可抽次数 **≈48 → ≈25 次**。既然它是"会一直被改的那类旋钮"，`tools/boss-balance/sim.mjs` 与 `ShopConfig.DEFAULTS` 都必须能改一处就跟上（前者已修，后者由 `audit:artifact` 的 **D1** 逐键盯着）。

- **广告未能播放 = 不发奖励（2026-11 修）**: `AdMgr` 未注入 provider 时**一律返回 false**（`isAvailable` 也是 false）。它曾经返回 true（"开发兜底按看完处理"），后果是遗物商店「金币不足 → 看广告免费刷新」在编辑器里被**静默白送**（玩家口径："有时候金币不足也能刷新"）。现在这条通道仍在（`adFreeDrawPerRun` 3 次/局），但**必须真的接上 SDK 才生效**；广告位不可用时，刷新按钮按"金币不够"置灰，`viaAd` 态会把费用图标换成广告图标（`RefreshButtonView`）—— 否则玩家会以为这一下要花金币。

- **局外属性进战斗（2026-11 落地）= 落到英雄的「基础属性」上，不是挂 Modifier**: 局外成长（图鉴里收集到的遗物）算出来的是一组 `OuterBonusGroup`（`flat` / `percent` 两层），**此前没有任何运行时消费点**（玩家在局外抽了一堆遗物，进局攻击力还是 `units.json` 里那个数）。现在唯一落点 = `battle/OuterAttributeApply.ts` 的 `applyOuterBonusesToEntity(hero, getAllEquipmentBonuses())`，由 `Scene_Game_Stage.selectHero` 在**创建英雄之后、`hero.bind()` 之前**调用。三条口径：① 公式 `final = base × (1 + percent) + flat` 与 `AttributeSystem.combine` 的结算顺序**逐字同构**（percent 先、add 后，都作用在 `base` 上），所以直接写进 `base` 等价于"这个英雄生来就有这么多基础属性"；② **落完必须把 hp/mana 重置到新上限** —— `Entity.Reinit` 里的 `hp = getMaxHp()` 是在局外加成**之前**跑的，不重置就是"上限涨了 200、当前血还是旧的"（开局第一帧残血）；③ **排在 `hero.bind()` 之前** —— 血条（`HpBar`）在 bind 时按当时的 `getMaxHp()` 建。**份数线性**：`getAllEquipmentBonuses()` 按收集份数线性累加（抽取可重复、同件无上限）⇒ 局外属性**没有天花板**（已知并接受，要收就在那一处 clamp）。**英雄页读数同源**：`HeroConfig.getAttrRows` 加了同一个第四参数 `outer`（由 `HeroVM` 递入，**刻意不让 `HeroConfig` 自己 import `EquipmentConfig`** —— 后者 import `DataCenter`、而 `DataCenter` import `HeroConfig`，那是循环依赖），且 `heroFingerprint()` 必须含「遗物 id × 份数」，否则抽到遗物切回英雄页属性不涨。**体检**：`npm run audit:attr` 的「局外专项」（**268 件逐件** + 空图鉴不动 / 收 3 份 = 3 倍 / 落完满血 / ~~缩放型属性落整百分点~~（⚠ **2026-11 起自动变成 ✅「局外一条比例型属性都没有」**）/ 接线位置在 bind 之前）+ `npm run audit:herocard` 的 F9 组。⚠ **2026-11 池子 37 → 268 件**（旧读数是"37 件逐件"），口径见 `tools/outer-relic-design/README.md`。
- **老存档的判据只能看「原始存档」（2026-11 踩过，`LevelData` 的旧档迁移从来没跑过）**: `DataModule` 的构造是「**先把默认值深度合并进来**」（`mergeDeep(defaults, saved)`），所以 `this.data` 里**永远有默认值里那份结构** —— 于是"这份存档里没有 `modes` 数组（= 模式功能之前的旧档）"这个判据**在 `this.data` 上永远不成立**，`ensureRecords()` 里那句"没有记录才迁移"被 `continue` 掉了整整一个版本，表现是**旧档的 `selected: 7` 被悄悄归成 `1`**（玩家丢了选中难度，且没有任何报错）。修法：在构造里用 `StorageUtil.getItem(key)` 读一次**合并之前的原始存档**，用 `!Array.isArray(raw.modes)` 判旧档，再迁移。**通用教训**：`mergeDeep` 之后"缺哪个字段"这个信息就**永久丢失**了 —— 凡是要按"老档缺了什么"做迁移/兜底的，判据必须落在**读盘那一刻的原始对象**上，不能在 `this.data` 上判。回归网：`npm run audit:mode` 的 C7/C7b（**验证过它会红**）。
- **赏金猎人攻击力 200 → 24（2026-11 修，`units.json#1002`）**: 全工程挂得最久的一处配表离群值（2026-10 的图标批次、`docs/hero-icons/README.md` 与 `tools/boss-balance` 都把它记成"疑似笔误、未改"；⚠ 同一行的攻击距离也是 200，很像复制错格）。**为什么不能留**：他的 `attack_interval` 是全表最短的 `0.85`（配 `攻速 120` ⇒ **1.41 次/秒**，全表最高），于是 200 攻的 Lv.1 普攻 DPS = **282**，是第二名（卓尔游侠 49.8）的 5.7 倍；做 Boss 强度对账时**他一个人的最终 Boss 墙钟 TTK 是 4 秒**，其余英雄 12~136 秒。**为什么取 24**：① 设计稿（`docs/prd/肉鸽塔防_英雄设计文档.md` §2.4/§3.1）写的是 **12（低）**，同级基准是狙击手 18 / 幻影刺客 32 ⇒ 按本作的火枪 40 / 幻影刺客 44 折算落在 **17~27**；② 24 正好是**全表最低档**（水晶室女同值），比同级物理输出（卓尔 32 / 斧王 34 / 火枪 40 / 幻影 44）明确低一档 —— 对应设计稿「清场效率低于纯输出英雄，战斗力来自经济差」；③ 另加一条下限判据：Lv.1 普攻 DPS = 24 × 1.41 = **33.9**，刚好压过 beat 1 的出怪流（⚠ 这个数是**当时**的 `SPAWN_BEATS[0]` = 1 只/1.33s × 哥布林 40 HP = **30 HP/s**；2026-11 前期加压后 beat 1 已改成 1 只/1.03s = **39 HP/s** —— 判据方向不变：33.9 略低于它，所以**开局前 1 分钟靠普攻清不完，必须去商店**，这正是加压想要的效果；再低就真是"开局第一批就打不完"了）。**副作用是好事**：`偷钱`（`modifiers.json` 13：`on_attack_landed → steal_gold 20`，**上限 = 目标携带的 `gold`**，怪身上是 40~600）偷到的钱随"打死一只怪要几下"变多 —— 200 时一击秒杀只能偷 20，24 时打 2~3 下能把一只哥布林身上那 50 掏空，**200 反而在砸他自己的被动**。**改完实测**（`node tools/boss-balance/sim.mjs --runs=40`，难度 1）：他的最终 Boss TTK **4s → 53s**、全表离散度 **4~136s → 53~124s**；四人组（定标基准，**不含他**）与中位两条线没有动 ⇒ `BossStrengthConfig.ts` 的倍率**不需要跟着改**。⚠ 他是 `Scene_Game_Stage.defaultConfig.heroUnitId`（默认英雄），所以这一改也是**开局手感变化最大**的一处；改表走 xlsx 管线（改 JSON → `node src/cli.ts json2excel --force --table units` → `npm run export` → `check` + `verify`）。
  · ⚠ **2026-11 后续：「副作用是好事」那一段的前提已经不存在了** —— 用户把赏金的技能从「命中偷 20 金币」改成**「每击杀 8 / 5 / 3 名敌人获得 1 金币」**（技能 3 级，随英雄 Lv.15 / Lv.30 升级；`abilities.json` 7 + `modifiers.json` 13 的 `script_id: Modifier_KillBounty`，口径见[技能与战斗系统](技能与战斗系统.md)「英雄技能随局内等级进化」）。**"攻击力越低、偷钱越多"这条反比关系没了**：现在收入只跟**击杀数**挂钩（谁打死算谁），与"打死一只怪要几下"无关。**24 这个值不用改**（它的三条依据里只有第 ③ 条是 DPS 下限判据，与偷钱无关），但**别再用"24 反而放大了他的被动"当理由**。代价是经济量级明显下滑（旧的偷钱是命中即偷、一轮能掏空一只怪身上的 40~600 金；新的是每 8 杀 1 金）—— **赏金从「经济引擎」变成「清场换钱」**，要不要补回这部分收益属于开放项（改之前先跟策划对目标：每局该多出多少金币）。
- **已知遗留噪声**: `ConfigLoader.nameToAttrId` 仍映射 17~20（lightningDmg 等）但 `AttributeType` 枚举只到 16；`ExcelConfigDecorator.ts`/`ITbDecode.ts` 等旧框架文件仍存在，新表一律走 `@tb_config` + `TbContainer` 管线（`Tb_*Config.ts`），勿新增旧式解码器。

## 2026-11 金币产出回收（「前期局外成长过快 / 局内前面太容易」）

**用户口径**：「金币产出要减少，现在我玩了几把，成就领了几千金币，遗物就抽了很多了，到前期局外成长过快，局内前面的难度太容易了」。
这是一次**因果链诊断**，不是"某个数字写大了"——下面四步是当时量出来的（全部用真表 / 真源码现算，没有手抄）：

### 1. 账面（改之前）

| 来源 | 改前 | 改后 |
|---|---|---|
| 成就 75 条（铜 / 银 / 金） | **185,650**（8,650 / 34,000 / 143,000） | **40,595**（1,945 / 7,050 / 31,600） |
| 账号升级 30 级 | 29,040 | **7,970** |
| 日任务 6 条 | 810 / 天 | **330 / 天** |
| 周任务 6 条 | 8,800 / 周（=1,257 / 天） | **2,800 / 周**（=400 / 天） |
| 商城·每日补给 | 200 / 天 | **100 / 天** |
| 商城·金币袋（广告 ×3） | 900 / 天 | **600 / 天**（200×3） |
| **一次性合计** | **214,690** | **48,565**（−77%） |
| **循环合计** | **3,167 / 天** | **1,430 / 天**（−55%） |
| 抽取阶梯 200/300/400/500/600 封顶 ⇒ 每天可抽 | **6 抽** | **3 抽** |

### 2. 根因两条（这是"为什么砍铜档、也砍日常"）

1. **一次性产出全压在铜档**：铜档 8,650 而**它 2~3 局就能全清** ⇒ 新手第一个晚上 ≈15,800 金 ≈ **16 抽**。
   注意这不是"总量太大"（总池 185,650 摊到几个月并不离谱），是**产出的时间分布**错了。
2. **日常循环 3,167/天 是设计稿假设的 3.9 倍**：`docs/meta-growth/README.md` §1.3 当年是按"日常 810 = 2 抽/天"对的账，
   而**商城金币袋 900 + 周常 1,257** 这两条在写那份账时**没算进去** ⇒ 实际是 6 抽/天。

### 3. 为什么"前期成长过快"会直接变成"局内前面太容易"

按真 `relics.json` 的 `modifiers_outer` 做 4,000 次抽样（以火枪 1001 为样本，裸装 atk 40 / hp 320 / 攻速 1.2）：

| 抽数 | 攻击 | 生命 | DPS 倍率 | HP 倍率 |
|---|---|---|---|---|
| 0 | 40 | 320 | ×1.00 | ×1.00 |
| 5 | 71 | 522 | ×1.92 | ×1.63 |
| **16** | **140** | **970** | **×4.42** | **×3.03** |
| 50 | 353 | 2,346 | ×17.75 | ×7.33 |

⇒ **一抽 ≈ +10% DPS / +8% 生命，且份数无上限**（`getAllEquipmentBonuses` 按份数线性累加）。
而局外属性是**从第 0 秒就落在英雄基础属性上**的（`OuterAttributeApply` 在 `selectHero` 里、`hero.bind()` 之前），
所以前 4 分钟的压力比 `L = S × 均HP ÷ 英雄DPS` 会从设计带的 0.55~0.96 **掉到 ≈0.15** —— 这就是"前面太容易"的实数。
**结论：金币是这条链的阀门，先拧它；不要去调怪物属性。**

> ⚠⚠ **2026-11 已改：上面这张表与"一抽 ≈ +10% DPS"整条作废**（局外遗物池重做，见 `tools/outer-relic-design/README.md`）。
> 它量的是**旧 37 件表**（当时的局外属性含攻速/暴击这类乘区，所以"前几抽"就抬得很陡）。新表：
> · 池子 **37 → 268 件**（= 局内池逐件相同），**份数 = 已收集总数 ÷ 池子件数** ⇒ 同一个份数对应 **7.24 倍**的抽数
>   （**0.05 份 = 13 抽** vs 旧表 2 抽）；所以上面的"5 抽 / 16 抽 / 50 抽"在新表里对应的份数小得多；
> · **"集齐一遍（268 件 × 1 份）"的总量与旧 37 件表基本持平**（DPS 平均 −5.1%、有效血 −4.7%），
>   但**同一笔金币买到的战力约为原来的 1/7** —— 也就是"前期成长过快"这件事**已经被这次重做压下去了**；
> · 局外属性只给 **5 条加法轴**（生命/魔法/攻击力/护甲/回血），**一条乘区都没有** ⇒ 曲线近似线性、不再"抽几件就爆"。
> **结论里那句"金币是这条链的阀门"仍然成立**（金币回收那一轮已落地），但"局外成长速度"这个变量**换了一把尺** ——
> 要重算"一抽值多少 DPS"，用 `node tools/difficulty-curve/recommend-anchors.mjs`（份数 → 面板倍率的官方读数：
> 0.05 份 ≈ 13 件 → ×3.45、1 份 = 268 件 → ×45.77）。

### 5. 「按局结算金币」的四条口径（写死在 `RunClearReward.ts` 的文件头，别在别处再算一遍）

1. **只有真正打完一局才发**：调用点是 `endRun()`（胜利 / 阵亡 / Boss 超时三条路都走它）；**中途退出**走 `exit()`、不调 `endRun` ⇒ 不发。
2. **乘一个完成系数** `clamp(到达阶段/3, 0, 1)`：堵"反复开局送死刷金币"（阶段 1 的怪几乎不破防，送死成本极低）。
3. **不乘难度收益倍率**（与 `grantClearHeroExp` 不同）：这条是**新手启动资金**，不是"高难度的报酬"；
   乘上去等于让老玩家用高难游戏档把刚回收掉的产出刷回来。
4. **局数 `N` 取自 `PlayerInfo.totalGames`** ⇒ 发奖必须排在 `reportRunTasks()` **之后**（`recordGameEnd` 在那里面 +1），
   排前面就永远差一局。
