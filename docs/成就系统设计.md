## 1. 定位与边界：成就 vs 任务

| | 任务 `tasks.json`（已有） | 成就 `achievements.json`（本系统） |
|---|---|---|
| 周期 | 日 / 周，**会重置** | **一次性、永久**，不重置 |
| 结构 | 一行 = 一条任务，单档 | 一行 = **一档**，同 `group` 的多行串成一条成就 |
| 奖励 | 账号经验 + 金币 | **金币**（低档）+ **金币 + 特殊效果**（核心成就的金档） |
| 目的 | 日常留存、给账号经验 | 长线目标感 + **永久成长（局内开局参数）** |
| 领奖 | 手动领取 | 手动领取（同一套交互 + 红点） |
| 数据模块 | `data/funcs/TaskData.ts` | `data/funcs/AchievementData.ts`（对称实现） |
| 配置门面 | `data/configs/TaskConfig.ts` | `data/configs/AchievementConfig.ts` |
| 容器 | `excel_table/Tb_TaskConfig.ts` | `excel_table/Tb_AchievementConfig.ts` |

**两者共用同一套「进度上报」**：`TaskData` 里那 12 个 `target` 词表就是成就的前 12 个词表，上报点（`Scene_Game_Stage` 的 8 处 + `reportRunTasks`）在现有 `taskData.addProgress(...)` 旁边**并排加一行** `achieveData.addProgress(...)`，不新增事件、不新增埋点框架。

## 3. 配表结构（`achievements.xlsx` / `achievements.json`）

### 3.1 为什么「一行 = 一档」，而不是「一行 = 一条成就 + 多档列」

| 方案 | 问题 |
|---|---|
| 一行一成就，档位用多列（`count1/count2/count3`、`reward1..3`、`effect1..3`） | 列数爆炸；每档奖励异构（金币 / 金币+效果）→ 只能写 `stringarray`，导表校验与门禁几乎无法做；加第 4 档要改表结构 |
| **一行一档 + `group` 分组（本方案）** | 每档一行、字段固定；**「已领到第几档」天然是一个游标**；加档只是加行；门禁可逐条校验（档位连续、阈值递增、效果只在末档） |

### 3.2 字段表

| 列 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | ✅ | 主键。段位：**31xx 等级 / 32xx 闯关 / 33xx 战斗 / 34xx 经济 / 35xx 收集 / 36xx 挑战**；段内 `id = 段首 + (成就序-1)*3 + (tier-1)` |
| `group` | string | ✅ | **成就组**（同一条成就的 3 档共用），如 `st_clear`。程序按它归并成一条展示 |
| `tier` | int | ✅ | 档位 1=铜 / 2=银 / 3=金（**必须从 1 连续**） |
| `category` | enum | ✅ | `level` / `stage` / `combat` / `economy` / `collect` / `challenge` |
| `name` | string | ✅ | 成就名（同一 group 三行写同一个名字，便于配表阅读） |
| `desc` | string | | 成就描述（列表副标题，可用 `\n`） |
| `icon` | string | | 图标资源路径（`textures/achievements/<group>`，**不带扩展名**，与遗物/技能同口径）；空 = 回落占位图 |
| `target` | enum | ✅ | 完成条件（词表见 §3.3） |
| `param` | string | | 条件参数（预留：如指定英雄/分类 id，留空 = 不限） |
| `count` | int | ✅ | 目标数量（累加型 = 需要累计到这么多；峰值型 = 需要达到这么多） |
| `reward_gold` | int | ✅ | **局外金币**（进 `ItemData.currencies.gold`） |
| `effect_code` | enum | | **特殊效果标识**（见 §5）；**只允许出现在该 group 的最大 tier 上**，留空 = 纯金币 |
| `effect_value` | int | | 效果数值（`effect_code` 非空时必填；百分比类填百分数：`10` = 10%） |
| `silent` | int | | `1` = 隐藏成就（达成前不展示）；缺省 0 |
| `sort` | int | | 同类内排序（升序） |

### 3.4 配表门禁（**三处落地，互相不可替代**）

| 落点 | 拦什么 | 什么时候报 |
|---|---|---|
| `schema.ts` 的 `enumValues` | `category` / `target` / `effect_code` **拼写错**（下拉框 + 校验） | `npm run check` / 导表时 |
| 容器 `AchievementCfgContainer.afterHandle()` | 结构错：档位不连续 / `count`·`reward_gold` 不递增 / 效果挂非末档 / 同一效果多来源 / `count ≤ 0` | 运行时 `console.warn` |
| **`npm run audit:achieve`**（`tools/achievement-audit/verify-achievements.mjs`，**39 条断言**） | 上面两处**漏掉的**：id 段位与分类不一致、隐藏成就跑到非挑战类、效果超封顶、死效果（白名单里没有成就来源）、金币梯度出区间、金币总量量级、以及**门禁本身的有效性（3 条负例）** | 违规退出码 1 |

规则清单（`audit:achieve` 逐条断言）：

1. 同一 `group` 的 `tier` 必须从 1 **连续无洞**，且 3 档齐（`tier = [1,2,3]`）；
2. `count` 与 `reward_gold` 在同一 group 内**严格递增**；
3. `effect_code` **只允许出现在该 group 的最大 tier**；
4. `effect_code` 必须在白名单（§5）内，且 `effect_value ≤ 该效果的封顶`；
5. **同一 `effect_code` 全表恰好 1 个来源**；且 10 个效果**每个都有成就来源**（无死效果）；
6. `id` 全局唯一，且**段位与分类一致**（31xx 等级 / 32xx 闯关 / 33xx 战斗 / 34xx 经济 / 35xx 收集 / 36xx 挑战）；
7. `count > 0`、`reward_gold > 0`、`name`/`desc` 齐备；`silent = 1` 只能出现在 `challenge` 类；
8. 金币梯度落在设计区间（铜 200~500 / 银 800~2000 / 金 4000~8000），金币总量落在 15~25 万量级。

> ⚠ **门禁必须被验证过**：`audit:achieve` 的 C 组会**故意喂坏数据**（中间档挂效果 / `count` 不递增 / 档位有洞），断言容器**一定会报警** ——
> 一张没人验过的门禁比没有门禁更危险（本项目已有先例：`retire-loose-skill-icons.py` 的"绝不删"名单里那句"无人引用"没人验，结果删掉了被预制件按 uuid 引用的图）。

## 4. 奖励口径

### 4.1 金币梯度（局外金币，进 `ItemData`）

| 档位 | 普通成就 | 核心成就（带效果） | 隐藏成就（挑战类） |
|---|---|---|---|
| 铜 `tier=1` | 200~400 | 200~400 | 500 |
| 银 `tier=2` | 800~1500 | 800~1500 | 2000 |
| 金 `tier=3` | 4000~6000 | 5000~6000 | 8000 |

- 对标现有经济：日任务 80~200 / 周任务 800~2400 / 账号升级 120~720（满级 30）。
- **全部 75 行清完的局外金币总量 ≈ 18.6 万**（见 §6 汇总），≈ 18 次周任务全清的量级，属于**长线一次性投放**，不会冲击周任务的必要性。
- 数量级直观参考：金档 5000 ≈ 3~4 次周任务；隐藏金档 8000 ≈ 半周的产出。

### 4.2 「只有高等级成就才有效果」的落地

- 效果**只挂在每条成就的末档（`tier` 最大那一行）**；
- 且**只有被标为核心的 10 条成就**在末档额外给效果，其余 15 条末档给大额金币；
- 所以「低等级成就的效果都是金币」在配表层面就是**事实**（`effect_code` 为空），不靠程序判等级；
- UI 上表现为：**铜/银档时卡片上的效果槽（2 个）是暗的/隐藏，到金档才亮起**（见 §7.4），玩家一眼能看出「这条成就的金档有额外奖励」。

### 5.2 生效时机与口径（**必须按这个来，否则数值会抖**）

1. **开局快照**：`Scene_Game_Stage.show()` 里读一次 `AchievementData.getEffects()` 得到 `{ code: value }`，**本局全程用它**；
2. **局中领奖不改本局**：局内领取的成就，效果**下一局**才生效（避免"打到一半突然多 50 金币/多一个商店选项"）；
3. **领奖即生效**：效果不是道具、不进背包、不需要装备；领取的那一刻写入永久记录，之后每局开局都带（`claimedTier` 推导，见 §8.2）；
4. **v1 不含属性类效果**：`OuterAttributeCalculator` / `EquipmentConfig.relicToBonusGroup` 的链路**尚未接线**（无运行时消费点），所以效果池刻意只做「局内开局参数 + 经济折扣」。等接线后再加 `attr_bonus` 一类效果。

### 5.3 为什么不叠加

- 每条 `effect_code` **全表只有 1 个来源**（门禁第 6 条保证），所以 10 个效果就是 10 个固定数值，**不需要运行时求和**；
- 但 `getEffects()` 仍按 `code → value` **求和**实现（并 clamp 到封顶），这样将来加第 2 个来源时**不用改消费方**，只有门禁需要放宽。

### 7.2 页面结构（编辑器里的节点契约）

> ✅ **节点已按本契约落地**（2026-10-03 在 `Scene_Menu.prefab` 里改的，编辑器里核过矩形）。三条实现口径：
> ① `lists` 的 `cc.Widget` **已拆掉** —— 它 `top=0 / bottom=1258` 会把 content 高钉成 0，和 `Layout(CONTAINER)` 打架；
> ② content 顶端下移到 **`y=557`**（页面高 1258，顶端 629）给 72 高的分类条让位，`Layout` 仍是 `VERTICAL/CONTAINER + spacingY 20 + padding 10`；
> ③ **容器一律锚点居中** —— 卡面 486×194（与英雄卡同骨架、同「卡间距 20」口径），
> 但 Cocos 里子节点坐标是相对**父节点锚点**的，锚点非居中的容器里子节点会整体偏出去（`detail/Label`、`unlock/*` 第一版就这么飞到卡外了）。
> `card` 在预制件里保持 `active=true`（看得见才好摆版），**运行时由 `Cmp_Achievement.onInit` 置 `active=false`**。

> ④ ⚠⚠ **ScrollView 必须挂在「视口子节点」上，不能挂在页面上（2026-10-03 进游戏连踩两次才定位到）**：
> `ScrollView` 的视口**取的是它自己所在的节点** —— `view` 这个序列化字段**根本不存在**（查过本预制件里
> 5 个 ScrollView，包括能正常工作的 `outer_relics/pages/overview`，都只有 `_content`；用代码 `sv.view = 子节点`
> 设的那一下**只活在内存里、存盘就丢**）。于是「把页面当视口」时 `_calculateBoundary()` 会把
> **content 顶端对齐到页面顶端**（`y=629`），`lists` 被从 557 顶到 629，第一张卡（顶部 619）
> **正好盖住分类条 557~629** —— 表现就是「分类条看不到」。
> 正解：视口**自成节点** `scroll`（546×1186 @ `y=-36`，上边留 72，带 `cc.Mask`，`ScrollView` 挂在它身上）——
> 它的顶端 557 = `lists` 顶端 557，两者对齐后互不推挤；分类条又在这个视口**之外**，结构上不可能再被盖住。
> （同口径可复用：`outer_relics` 的 `pages/overview` / `attrs` 就是「ScrollView 挂在视口节点上」的现成例子。）

```
content/right/achivements            ← [Cmp_Achievement]（**不再是 ScrollView**，只是页面宿主：分类条 + 视口的共同父节点）
├── scroll                           ← 滚动视口（ScrollView 挂这里 + Mask 矩形裁切；Widget top=72 其余撑满）
│   └── lists                        ← Layout(V)，成就卡片的容器（锚点 0.5,1；顶端 = 557）
│       └── card                     ← 唯一的卡片 = **克隆模板**（照 Cmp_OuterRelics 的 templates 套路）
│           ├── bg
│           ├── icon
│           │   ├── inner            ← 成就图标
│           │   └── lock             ← 未达成遮罩（mask + icon）
│           ├── name                 ← Label 成就名
│           ├── lv                   ← Label 档位
│           ├── detail/Label         ← Label 描述 + 进度
│           ├── unlock               ← 奖励区 / 领取按钮（带 Button）
│           │   ├── Label
│           │   ├── icon             ← 金币图标
│           │   └── value            ← Label 金币数量
│           ├── weapon  / weapon-001 ← 2 个「效果槽」
│           └── property ×4          ← 4 行「效果明细」（icon + name + value）
└── category_bar                     ← ✅ 已落地（6 个 cat_* 按钮），在滚动区**之外**，压不住
```

**列表铺法**（与 `Cmp_OuterRelics` 完全同套路，坑也照抄）：
1. `card` 当**模板**：`onInit` 里 `card.active = false` 存起来，铺列表时 `instantiate` 克隆；
2. 生成的行统一命名 `row_<group>`，`clearGenerated()` **只清 `row_` 前缀**（`lists` 里将来作者摆的标题/空态节点不能被清掉）；
3. 清行必须 **先 `removeFromParent()` 再 `destroy()`** —— `destroy()` 延迟到帧末，只调它会让 `Layout` 按双倍行数算高度（画重叠列表）；
4. 数据层没就绪（`TbRoot` 未加载）时**不要抛异常**（会连带弄坏整个 `Scene_Menu`）：退化成空页 + `ezgame.error`，等下次 `onShow` 重试。

## 8. 数据结构与接口（`AchievementData`）

### 8.1 存储形状

```ts
/** localStorage key = 'achievement_data'（DataCenter 统一 save/reset/export） */
export interface IAchievementData {
    /** 进度记录（**数组**！见下方 ⚠） */
    records: AchRecord[];
    /** 累计领取档数（统计用） */
    claimedTotal: number;
    /** 买过的击杀商店 Buff 种类（id 列表，`buff_types` 的数据源） */
    buffTypes: number[];
    /** 抽到过的肉鸽技能种类（id 列表，`skills_picked` 的数据源） */
    skillKinds: number[];
}

export interface AchRecord {
    /** 成就组（= 配表 group） */
    group: string;
    /** 当前进度（累计型只增；峰值型取历史峰值） */
    progress: number;
    /** 已领到第几档（0 = 一档都没领） */
    claimedTier: number;
}
```

> ⚠ **`records` 必须是数组，不能用 `{ [group]: record }` 字典**：`DataModule.mergeDeep` 只合并「默认数据里已经存在的 key」（`if (!(key in target)) continue`），动态字典 key 在**读档时会被整片丢掉**（`TaskData` 头注释记的就是这个坑）。数组走"整片覆盖"，能正确读档。

### 8.2 接口（对称 `TaskData`）

```ts
// ── 上报（对局侧；与 taskData 并排一行） ──
achieveData.addProgress('kill_enemies', 1);       // 累加型
achieveData.peakProgress('stage_reached', 5);     // 峰值型（只增不减）
achieveData.markFlag('first_clear');              // 置为完成（flag 型）

// ── 查询（界面侧） ──
achieveData.getGroups(category)      // 某分类的成就（已归并 group + 按 sort 排序 + 隐藏过滤）
achieveData.getGroupState(group)     // { tier, progress, count, state, nextReward, effects }
achieveData.getClaimableCount()      // 红点
achieveData.getProgress(group)       // 进度（钳到当前档目标）

// ── 领奖（唯一发奖口） ──
achieveData.claim(group)             // 领"下一档"；先落盘 claimedTier 再发奖（防连点双发）

// ── 效果（开局快照） ──
achieveData.getEffects()             // { [effect_code]: value }（已 clamp 到封顶）
```

> **as-built（2026-10-03，实现时按此收敛，字段名以 `AchievementData.ts` 为准）**
> · `getGroups(category?)` 返回的是 `AchGroupState[]`（不是配表行）——判据**只在数据层算一次**，界面不重算；
> · `AchGroupState` 字段：`group / category / name / desc / icon / silent / tier(展示档) / nextTier / claimedTier /
>   maxTier / progress(钳到**下一档**目标) / count / state / nextReward / effect / effectUnlocked / hidden`；
> · `state` 是**四态**（比 §7.4 的三态多一个"领完"）：`active`(下一档未达成) / `claimable` / `claimed`(本档已领、下一档未达成) / `done`(全档领完)；
> · 另有两个 C 类计数的写入方：`addBuffType(buffId)` / `addSkillKind(skillId)`（**只认新种类**，进度语义是「种类数」）；
> · `syncNonRunPeaks()` = 对齐「不需要打一局就会变」的峰值（账号等级 / 连续登录 / 遗物种类数 / 两个种类集合），由 `DataCenter.init()` 与成就页 `onShow` 调用，**幂等**。

### 8.3 与 `TaskData` 的**必要差别**（实现时别照抄错）

| 点 | `TaskData` | `AchievementData` |
|---|---|---|
| 领取状态 | `claimed: boolean`，领完**不再累积进度** | `claimedTier: number`，**领完继续累积**（否则领了铜档后银档永远卡住） |
| 进度来源 | 周期重置 | **永不重置** |
| 发奖 | 账号经验 + 金币 | **只有金币**（`ItemData.addCurrency(Gold)`）+ 副作用（效果永久生效） |
| 配置查询 | `getByTarget` 反查 | 多一个**按 group 归并**（同 group 三行 → 一条展示数据） |
| 额外状态 | — | `buffTypes` / `skillKinds` 两个"种类集合"（收集类成就的数据源） |

### 8.4 `DataCenter` 注册（照 `taskData` 的现有套路）

- 新增字段 `achieveData = new AchievementDataModule()`；
- `init()`：`_migrateIfNeeded` 之后上报一次「等级 / 连续登录 / 图鉴 / 种类数」这类**不需要对局**的峰值（否则要等玩家打一局才动）；
- `saveAll` / `resetAll` / `exportAll` / `importAll` / `disposeAll` / `resetModule` 六处**都要加上它**（漏一处就是"存档丢一半"或"重置不干净"）；
- 发奖走 `DataCenter` 一层（与 `grantTaskReward` 对称）：`grantAchieveReward(gold, group)`，内部 `itemData.addCurrency` + `saveAll()`。
